접속이 안 될 때 원인을 찾는 순서, 실습이 끝난 뒤 요금이 나오지 않게 정리하는 방법, 그리고 B3-1 구조의 한계를 정리했습니다.

## 가설을 세우고 하나씩 검증하기

설정을 이것저것 바꿔 보면 무엇이 원인이었는지 알 수 없고 되돌리기도 어렵습니다. 그래서 증상을 보고 원인 후보(가설)를 세운 뒤 명령어로 하나씩 확인해 지워 나갑니다.

| 사례 | 증상 | 확인한 원인 | 조치 |
|---|---|---|---|
| 외부 접속 실패 | 브라우저 접속 불가, SSH는 됨 | 보안 그룹에 HTTP 80 규칙 없음 | 80 인바운드 추가, 스크립트에 포함 |
| SSH 거부 | `Permission denied (publickey)` | `.pem` 파일 권한 644 | `chmod 400`, 스크립트에서 자동 실행 |
| EC2 생성 거부 | `UnauthorizedOperation` | IAM 정책의 리전 조건 때문에 일부 차단 | 조건을 고쳐 필요한 범위만 허용 |

## 외부 접속이 안 될 때 확인 순서

```
1. 라우팅: 라우팅 테이블에 0.0.0.0/0 → IGW가 있고 서브넷에 연결됐나
2. 보안 그룹: 인바운드에 해당 포트가 열려 있나
3. 퍼블릭 IP: 인스턴스에 퍼블릭 IP가 있나
4. 서버 프로세스: systemctl status nginx, curl localhost
5. 로그: /var/log/nginx/error.log, /var/log/syslog
```

바깥(네트워크)에서 안쪽(서버)으로 좁혀 들어가는 순서입니다. SSH는 되는데 웹만 안 되면 라우팅과 퍼블릭 IP는 정상이니 보안 그룹부터 보면 됩니다.

## 리소스 정리

AWS는 리소스가 켜져 있거나 남아 있기만 해도 요금이 나올 수 있습니다. 서로 의존하는 리소스는 아래 순서로 지워야 상위 리소스를 지울 수 있습니다.

```
EC2 종료 → 남은 EBS 볼륨·Elastic IP 정리 → IGW 분리 후 삭제
 → 서브넷 → 라우팅 테이블 → 보안 그룹 → VPC → 키 페어
```

| 남겨 두면 요금이 나올 수 있는 것 | 이유 |
|---|---|
| EC2 | 실행 시간만큼 (프리 티어 한도를 넘으면) |
| EBS 볼륨 | 인스턴스를 지워도 볼륨이 남으면 용량만큼 |
| Elastic IP, 퍼블릭 IPv4 | 퍼블릭 IPv4 주소는 시간당 요금 |
| NAT 게이트웨이, 로드 밸런서 | 만들어 두기만 해도 시간당 요금 |

B3-1에서는 모든 리소스 이름을 `cloud-lab-`으로 시작하게 태그를 달고 `cleanup-infrastructure.sh`가 이 태그로 삭제 대상을 찾아 순서대로 지우게 했습니다. 마지막에는 결제 대시보드에서 요금이 더 나오지 않는지 확인했습니다.

## B3-1 구조의 한계

- **AZ 하나에 서버 하나입니다.** 그 AZ나 서버에 문제가 생기면 서비스가 멈춥니다. 여러 AZ에 서버를 두고 로드 밸런서로 묶어야 장애를 견딜 수 있습니다.
- **EC2가 퍼블릭 서브넷에 바로 노출돼 있습니다.** 실무에서는 로드 밸런서만 밖에 두고 서버는 프라이빗 서브넷에 둡니다.
- **HTTP만 씁니다.** 도메인과 HTTPS 인증서가 없어서 주고받는 내용이 암호화되지 않습니다.
- **퍼블릭 IP가 바뀔 수 있습니다.** 자동 할당 IP라서 인스턴스를 중지했다 켜면 주소가 바뀝니다. Elastic IP나 도메인이 없습니다.
- **SSH 22번 포트와 키 파일로 관리합니다.** 내 IP로 막아 두긴 했지만 포트를 아예 열지 않는 Session Manager 같은 방법도 있습니다.
- **셸 스크립트는 상태를 기억하지 못합니다.** `setup-infrastructure.sh`를 한 번 더 실행하면 같은 리소스를 또 만듭니다. Terraform 같은 IaC 도구는 지금 상태와 비교해서 바뀐 것만 반영합니다.
- **IAM 권한이 작업 단위에서만 좁혀져 있습니다.** 대부분 `Resource: "*"`라서 다른 VPC나 인스턴스도 건드릴 수 있습니다. 또 트러블슈팅 문서에는 리전 조건을 고쳤다고 적었지만 저장소의 `setup-iam.sh`에는 `ec2:Region` 조건이 그대로 남아 있습니다.
- **모니터링과 로그 수집이 없습니다.** 서버가 죽어도 알림이 오지 않고 로그를 보려면 서버에 직접 들어가야 합니다.

## 면접에서 나올 만한 질문

### Q. EC2에 올린 웹 서버에 외부에서 접속이 안 되면 어떤 순서로 확인하나요?

증상을 보고 원인을 좁혀 가는 순서가 있는지 봅니다.

> 바깥에서 안쪽 순서로 봅니다. 라우팅 테이블에 IGW 경로가 있고 서브넷에 연결됐는지, 보안 그룹 인바운드에 80번이 열렸는지, 인스턴스에 퍼블릭 IP가 있는지 확인합니다. 그다음 서버에 들어가 Nginx가 실행 중인지, `curl localhost`가 되는지, 에러 로그를 봅니다. B3-1에서는 SSH는 되는데 웹만 안 돼서 보안 그룹부터 봤고 80번 규칙이 빠진 것을 찾았습니다.

### 꼬리질문

- 리소스를 지울 때 순서가 왜 중요한가요?
  → VPC 안에 서브넷이나 보안 그룹이 남아 있으면 VPC가 지워지지 않는 것처럼, 의존하는 리소스가 남아 있으면 상위 리소스를 지울 수 없기 때문입니다.
- 이 구조를 실제 서비스로 바꾼다면 무엇부터 바꾸겠어요?
  → 서버를 프라이빗 서브넷 두 AZ에 나눠 두고 퍼블릭 서브넷의 로드 밸런서에서 HTTPS를 받게 바꾸겠습니다. 인프라는 Terraform 같은 IaC로 옮기겠습니다.
